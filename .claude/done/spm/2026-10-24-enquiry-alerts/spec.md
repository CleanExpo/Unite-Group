## 1. Task and outcome

When someone submits the public enquiry form, Phill gets an email within seconds saying who it is and what they want, with the full details behind a link to the enquiry in the app, and a buyer is never dropped because an alert failed or went missing. The same applies when the card payment account reports a checkout.

Must not happen: an alert failure blocks or rolls back the lead insert; the alert leaks the full lead row; an alert is lost without the health read going red; an agent registers the Stripe endpoint or sets a production env var.

## 4. Design

### 4.1 Types and entry point
`notify()` becomes overloaded on a discriminated union keyed by `type`:
- legacy variant (existing seven types, `title`/`body`/`severity`/`metadata`): returns `Promise<void>` exactly as today.
- `{ type: 'new_lead'; leadId; firstName; businessName | null; interests | null; capturedAt }`: returns `Promise<NotifyResult>`.
- `{ type: 'checkout_completed'; event: Stripe.Event }` (covers the three checkout event types): returns `Promise<NotifyResult>`.

`NotifyResult = { email: Outcome | 'deduped' }` with one exported `Outcome = 'sent' | 'failed' | 'unconfigured'` and `LogOutcome = Outcome | 'pending' | 'deduped'`, used by both the writer and the health read. The lead variant has no email, phone, surname, message or IP key, so adding one is a compile error. `notify()` never throws. There is no separate `notifyNewLead`; `/api/leads` calls `notify({type:'new_lead',...})` directly.

For these two kinds `notify()` does not use the existing early returns: delivery needs only the env settings in 4.3, so `FOUNDER_USER_ID` unset or a `user_settings` read error never suppresses it. If the email env is missing the outcome is `unconfigured`.

### 4.2 Alert content (built by a pure `buildAlertText`, never via title or metadata)
Lead alert lines, in this order: first name, business name, the ask, a link to the enquiry in the app, and `Ref: <lead id>` (the lead id is an internal uuid, not personal data; it lets Phill find and erase the mailbox copy). Nothing else. Phone, email, surname, the full message and IP are never in the alert; the person reads them in the app after following the link.
- The ask: the package label. A `GROW_PACKAGES` id maps to its name; `living-card` or `living-card:<edition>` maps to "Living card" plus the edition when it is a known edition name; anything else "Not specified". The label for a known edition is `Living card: <edition>`.
- First name and business name: control characters stripped, truncated to 80, HTML-escaped in the email. A missing business name reads "Not given".
- Link: `NEXT_PUBLIC_APP_URL` (default `https://unite-group.in`; an http(s) URL without credentials, else the send fails) plus `/founder/leads/<lead id>`. The link sits behind the app's sign-in, so it carries no personal data itself.
- Email subject is the fixed string "New enquiry". For these two kinds `title` is the fixed string "New enquiry" or "Checkout alert" and `metadata` is limited to `{ source_id, package_label }` (the console audit line is printed by the alert path itself) (or the event id suffix), so the console audit line carries no personal data.

Checkout alert lines: status, amount converted from minor units first (divide by 10 to the power of the currency's fraction digits, read from `new Intl.NumberFormat('en-AU',{style:'currency',currency}).resolvedOptions().maximumFractionDigits`), then formatted with `Intl.NumberFormat` currency style (`Intl.NumberFormat` formats major units and does not convert), `livemode`, last 8 characters of the event id, UTC timestamp. No customer name, email or address.
- `checkout.session.completed` with `payment_status` of `paid` or `no_payment_required`: "Payment received". With any other status: "Checkout started, awaiting payment".
- `checkout.session.async_payment_succeeded`: "Payment received".
- `checkout.session.async_payment_failed`: "Payment failed".

### 4.3 Channel (email only)
- Email: `sendEmail` to env `LEAD_ALERT_EMAIL_TO` from `SENDGRID_FROM_EMAIL`. In Production `LEAD_ALERT_EMAIL_TO` is `contact@unite-group.in`; Preview uses a different test address so a preview test never reaches the real mailbox. If `LEAD_ALERT_EMAIL_TO`, `SENDGRID_API_KEY` or `SENDGRID_FROM_EMAIL` is unset the outcome is `unconfigured`, decided before calling `sendEmail` (not by parsing its error).
- There is no other channel. The existing Slack environment variables are not read by these alerts.
- SendGrid is called on its own `MailService` with `setTimeout(min(5000, 6000 - elapsed - 500))` milliseconds, so it always times out before the 6-second cap; with under 1 second left no send starts and the outcome is `failed`. Click and open tracking are disabled on the message (no link rewriting, no pixel). No retries at any layer; reconciliation (4.6) is the backstop.
- Suppression: SendGrid returns 202 for a recipient on its suppression lists and then drops the mail. The health read (4.6) therefore checks the destination against the bounces, blocks, spam reports, invalid emails, unsubscribes and global unsubscribe lists, which needs a key with the Suppressions Read scope; without it the answer is `unknown`, never `clear`.
- Logging on this path prints `error.name` and an HTTP status only, never `error.message`, because a provider error message can echo request details such as the recipient address or key.

### 4.4 /api/leads
Insert `crm_leads` returning `id, captured_at`. After a successful insert, and before the response, one block runs under a 6-second cap in the route, and `notify` applies the same 6-second cap itself with an abort signal that covers the lead lookup, the claim, the send and the log write. Every exception and the cap are caught; an alert that has not resolved returns `failed`. When the cap fires the abort stops the log update, so the claimed row stays `pending` and the health read counts it as failed after 15 seconds. The route sets `export const maxDuration = 30`. The response body is exactly what it is today on every alert outcome (`{ id }` or `{ id, drip }`); no field reveals alert or dedup state (a public route must not expose whether an email was seen recently). A 400 or 500 path sends no alert.

Atomic claim and dedup. Before sending, `notify()` calls the SQL function `claim_alert(p_founder uuid, p_kind text, p_source_id text, p_dedup_key text, p_window_minutes int)` through the service-role client. For leads, `notify` reads the lead's email from `crm_leads` by lead id and `p_dedup_key` is the hex HMAC-SHA256, under the server secret `ALERT_DEDUP_SECRET`, of `founder_id|lower(email)|package_label` (no raw email is stored, and the value cannot be recomputed from an email address alone). When `ALERT_DEDUP_SECRET` is unset the key is null: the alert still sends, duplicate suppression is off and one console line names the variable. For checkout (S2b) it is null. Inside one transaction the function:
1. when `p_dedup_key` is not null, takes `pg_advisory_xact_lock(hashtextextended(p_dedup_key, 0))`, which serialises every concurrent claim for the same buyer and package whatever order their lead rows became visible;
2. when `p_dedup_key` is not null, checks coverage: a row for the same `founder_id` and `source_kind`, a DIFFERENT `source_id` and the same `dedup_key`, created within `p_window_minutes` (60), whose `outcome` is `sent`, or `pending` and created less than 15 seconds ago (in flight). `failed`, `unconfigured`, `deduped` and stale `pending` rows never cover. If covered, it inserts this source's row as `deduped` (`ON CONFLICT DO NOTHING`) and returns no channels;
3. otherwise it claims with `INSERT INTO alert_delivery_log (founder_id, source_kind, source_id, channel, outcome, dedup_key) VALUES (...) ON CONFLICT (source_kind, source_id, channel) DO NOTHING RETURNING channel` for `email` as `pending`, and returns the channels the insert returned (at most `email`).

`notify()` sends on exactly the channels returned, then updates each row to `sent`, `failed` or `unconfigured`. The unique constraint makes the claim idempotent per source (a replay or retry gets no channels and sends nothing); the advisory lock makes dedup across different leads atomic, so two concurrent double-submits produce one email in total, and the result does not depend on which insert committed first. Consequences by design: a first lead whose alert failed never suppresses a resubmission; a second enquiry for a different package has a different key and is never suppressed. A `pending` row older than 15 seconds (process died after claiming) counts as `failed` in the health read. If the `claim_alert` call itself errors, the alert is sent without a claim (fail toward a duplicate ping, never toward silence) and `unalerted` (4.6) reports the source. Both lead rows are always stored.

### 4.5 Delivery log
Migration `apps/web/supabase/migrations/<ts>_alert_delivery_log.sql` (header carries PENDING SANDBOX VERIFICATION and the rollback line; `create table if not exists`, so a name collision no longer fails loudly: `to_regclass` proves only the name, and the release check must also query the unique constraint and the function;  policies in `pg_policies`-guarded DO blocks). One row per source per channel. Email is the only channel, so in practice one row per source; the `channel` column and its place in the unique key are kept (check allows `email` only) so a second channel can be added later by a forward migration that widens the check, without reshaping the table:
- `id uuid primary key default gen_random_uuid()`
- `founder_id uuid not null references auth.users(id) on delete cascade`
- `source_kind text not null check (source_kind in ('new_lead','checkout_completed'))`
- `source_id text not null` (lead id or Stripe event id; deliberately no foreign key so evidence outlives a deleted lead; say so in the header)
- `channel text not null check (channel in ('email'))`
- `outcome text not null check (outcome in ('pending','sent','failed','unconfigured','deduped'))`
- `dedup_key text` (nullable; hex SHA-256, leads only)
- `created_at timestamptz not null default now()`, `updated_at timestamptz not null default now()`
- `unique (source_kind, source_id, channel)`; index on `(dedup_key, created_at desc) where dedup_key is not null`; index on `(created_at desc)`.
- the function `claim_alert` (4.4), with `execute` revoked from `public`, `anon` and `authenticated` and granted to `service_role` only.

RLS is enabled and forced to match `crm_leads`; the founder-only select policy copies the crm_leads policy; the service role is the only writer. Rows are written once per claim and updated once to a final outcome; there is no delete policy for any role. Deletion happens only through `erase_lead_alert_data` (below), for which the second migration grants `delete` on the table to `service_role`; this is convention, not a database guarantee. No lead fields are stored. No retention job in this slice (DEFERRED; the purge job is not built and the policy promises erasure on request only). The table holds the lead id and the keyed `dedup_key`, both pseudonymous.

Erasure: forward migration `apps/web/supabase/migrations/20261025000000_alert_erasure.sql` adds `erase_lead_alert_data(p_founder, p_lead_id, p_dedup_key)` (service_role only), which deletes the lead's log rows by source id and by key, and its `crm_timeline_*` `agent_actions` rows (matched by lead id, as that table has no founder column). The founder-only route `POST /api/founder/leads/[id]/erase-alert-data` proves the lead belongs to the founder, then erases every enquiry that shares the email. It does not delete `crm_leads` or the mailbox copy; both stay manual steps named in the privacy policy. This migration ships before or with the code; without it the route returns 500 and reports nothing erased.
`founder_id` for the log comes from `FOUNDER_USER_ID`. On the lead path that variable is already required (the route returns 500 before inserting when it is unset, so no lead, no claim and no alert exist in that case; nothing is promised beyond that 500). On the checkout path (S2b), if it is unset no claim can be written (the column is NOT NULL and an invented owner is not acceptable): the alert is still attempted without a claim, the code prints a console error naming the variable, and `unalerted` (4.6) reports the event.
Rollback is a code revert only; the table and function are additive and stay. If it is ever removed it goes through a forward migration, never a raw DROP, which would leave the migration ledger saying it is applied. The file lives in `apps/web/supabase/migrations/` and nowhere else (not `manual-applies/`, not the nested legacy tree). Phill applies it to production.

### 4.6 Health read and reconciliation
`GET /api/health/alerts`, bearer auth. The token accepted is `ALERT_HEALTH_TOKEN` if set, else `CRON_SECRET` with `assertCronAuth` semantics (unset or blank never authenticates). If `ALERT_HEALTH_TOKEN` equals `CRON_SECRET` the route returns 500 and does not read anything, because a read-only counter credential must not be the cron master key. The heartbeat workflow uses `ALERT_HEALTH_TOKEN` as a GitHub secret. Every count covers the same 72-hour window. With a daily poll this means a lead captured, or a failure logged, just after one poll (inside the 2-minute grace, or even a minute after) is still inside the window at the next poll, so nothing can fall between two polls; the cost is that a failure keeps the gate red until it ages out or is resolved, which is intended. Response:
`{ window_hours: 72, attempts, failed, unconfigured, deduped, unalerted, last_failure_at, sent, delivery_note, destination, failed_ids, unalerted_ids }` (`sent` counts sources with a `sent` row; `destination` is `clear`, `suppressed` or `unknown` per 4.3; the two id lists are sorted and capped at 20 lead ids, so the issue names who to follow up), counted per source (a lead or a checkout event); with email as the only channel that is one log row per source.
- `attempts` counts sources with at least one non-`deduped` row. `failed` counts sources where any channel row is `failed` or `unconfigured`, or `pending` and older than 15 seconds. `unconfigured` counts sources where any channel row is `unconfigured`. `deduped` counts sources whose rows are all `deduped`.
- `unalerted` = `crm_leads` rows (`captured_at`) older than 2 minutes and inside the window with no `alert_delivery_log` row where `source_kind='new_lead'` and `source_id = crm_leads.id::text`; plus sources whose rows are all `deduped` while no other source with the same `dedup_key` has a `sent` row in the preceding 60 minutes (a suppression with nothing behind it); plus, from S2b only, `stripe_events` rows (`received_at`, joined on `stripe_events.stripe_event_id = source_id` with `source_kind='checkout_completed'`, not the UUID `id`) of the three checkout types received after the constant `CHECKOUT_RECON_FROM` set in the S2b PR to its deploy date. In S2a the checkout term is absent, so checkout events with no handler yet cannot turn the gate red. This catches a dead call site, a crash after insert, a failed claim and a suppression with nothing behind it.
- Healthy means `failed = 0 and unalerted = 0 and destination is not suppressed`. If either table cannot be read, or `FOUNDER_USER_ID` is unset, the route returns 503, never zeros. `last_failure_at` is the latest `updated_at` of a failed row (or `created_at` of a stale pending row), and is read as any ISO-8601 instant with a Z or +hh:mm offset.

The daily heartbeat (`.github/workflows/nexus-heartbeat.yml` and `scripts/nexus-heartbeat.mjs`) gains a fourth declared gate, `alert-health`, whose captured evidence is the route's response and exit status, so it reaches the issue composer: the gate is FAIL on non-200, a response that does not match the expected shape, `failed > 0`, `unalerted > 0` or a `suppressed` destination, and NOT RUN when no evidence arrived (never green). Escalation is the existing GitHub issue, not the alert email, since that is the channel under test. The issue body also lists the lead ids to follow up, states when the destination is suppressed or not checked, and calls out a repeat failure when the counts rose since the previous run (a red gate would otherwise hide a second outage). Detection delay is up to 24 hours.
`sent` means the provider accepted the message (SendGrid 202), not that it was delivered.

### 4.7 Checkout handler (phase S2b, gated)
Phasing (chair ruling): lead alerts (4.1 to 4.6 without the checkout terms; AC-1 to AC-7, AC-9 to AC-11, AC-13 to AC-15) ship first as S2a. Everything that needs a checkout handler or checkout reconciliation (this section, AC-8, AC-12) is S2b only. The read-only proof of demand is `stripe events list --type checkout.session.completed --limit 5` on the card payment account, run by Phill.
In the Stripe route, after the `stripe_events` insert succeeds (not on the 23505 path), for `checkout.session.completed`, `checkout.session.async_payment_succeeded` and `checkout.session.async_payment_failed`, call `notify({type:'checkout_completed', event})` under the same cap and claim rules (no dedup key, so the unique `(source_kind, source_id, channel)` constraint is the only gate and a replay of one event id sends nothing). ## 6. Security and privacy

- Minimisation: alert text is built only from the allow-listed fields in 4.2 (first name, business name, the ask, the link); no title or metadata carries personal data. Phone, email, surname, full message and IP stay in the app behind the link.
- Disclosure: sending a visitor's first name and business name to the alert mailbox via SendGrid puts it with a processor the privacy policy does not list, overseas, with retention set by that account. Phill's decision of 24/10/2026 fixes the alert content, so the policy edit is a required PR item, not an open question: the PR adds SendGrid to the processor table, amends the sentence saying enquiries are held only in Supabase, and adds an erasure step naming who deletes the alert email when a deletion request is actioned. Phill approves the wording when he reviews the PR.
- Secrets: API keys and the recipient address are never logged (4.3). The health read returns counts only.
- Stripe signature verification stays the first gate.

## 7. Failure behaviour

| Failure | Result |
|---|---|
| Email send fails (SendGrid down or rejects) | 201; the row records `failed`; `failed` +1 |
| Email unconfigured (`LEAD_ALERT_EMAIL_TO`, key or from-address unset) | 201; row `unconfigured`; `failed` +1 |
| Lead path, `FOUNDER_USER_ID` unset | existing behaviour: 500 before the insert; no lead, no claim, no alert |
| Checkout path (S2b), `FOUNDER_USER_ID` unset | alert attempted without a claim; console error naming the variable; health `unalerted` +1 |
| Alert path throws | 201; the row is updated to `failed` |
| The 6 s cap fires | 201; the abort stops the log update, so the claimed row stays `pending` and counts as `failed` after 15 s |
| Destination on a SendGrid suppression list | the send is accepted (202) and `sent` is recorded; the health read reports `destination: suppressed` and the gate is red |
| `claim_alert` call errors | alert is sent without a claim; health `unalerted` +1 |
| Process dies after the insert, before the claim | health `unalerted` +1 after 2 minutes |
| Process dies after the claim, before the update | row stays `pending`; counts as `failed` after 15 s |
| Log table unreadable | health 503 |
| Duplicate buyer and package within 60 minutes, concurrent or not | exactly one email; the other source's row is `deduped` |
| `ALERT_DEDUP_SECRET` unset | alert sends with no claim key; no duplicate suppression; console line names the variable |
| Replay of the same lead or Stripe event | no channels returned; no second alert |
| BECS or other delayed payment (S2b) | "awaiting payment", then one "Payment received" or "Payment failed" |
