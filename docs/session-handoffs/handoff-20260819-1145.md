## 4. The blocking finding (P0) — the fix would have caused an outage

Revoking EXECUTE on `get_my_org_ids` from `authenticated` breaks every RLS policy that
calls it. **Postgres checks function EXECUTE against the QUERYING role when it evaluates a
policy expression; `SECURITY DEFINER` on the callee does not exempt it** — that governs
whose rights the body runs with, not who may invoke it.

`public.organizations` carries orgs_all / orgs_select / service_orgs policies that are
org-membership-scoped via `get_my_org_ids()`
(`apps/empire/supabase/migrations/20260513180500_notifications_projects_organizations.sql:60`).
So the revoke makes every authenticated read of that table fail with
`ERROR: permission denied for function get_my_org_ids`. The only recovery is the rollback,
which re-opens the anon-callable JWT-minting hook.

**Reproduced independently** on PG 17.6, on the broken query shape (a table read, not a
direct function call): 1 row before the revoke, hard error after, with
`proacl = {postgres=X/postgres}` and `has_function_privilege('authenticated',…) = f`.

**The first attempt at that reproduction was wrong and is recorded as such.** It revoked
only from `authenticated` and showed no breakage — because PUBLIC's language-default `=X`
grant still supplied the privilege. An unbroken read after a partial revoke proves nothing.

**No control caught it.** Step 6's negative control only probes `harmless_rpc()`, which is
not on the revoke list, so it is structurally incapable of detecting over-reach onto a
listed function.

**Scope limit, stated plainly:** what is proven is the mechanism. What is **not** proven is
that production's `organizations` policies specifically fail — the migration defining them
is prod-only, part of the documented 95-migration drift, so the policy bodies cannot be
read from here. The evidence is the in-repo comment plus the reproduced mechanism. That is
still blocking: this file gets pasted into production by hand, and "probably no policy calls
it" is not a basis for that.
