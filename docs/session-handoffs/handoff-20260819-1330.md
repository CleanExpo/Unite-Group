## 2. The substantive finding — a guarantee with no control

`repro-prod-exposure.sh` step 5 asserted, after the fix, that
`supabase_auth_admin` still holds EXECUTE on both auth hooks — the check standing
between this migration and a total login outage, which is the one way the fix
could be worse than the exposure it closes.

**Deleting the `GRANT EXECUTE … TO supabase_auth_admin` re-grant from the fix
left the harness GREEN — exit 0, "login survives" printed.** Measured, not
reasoned.

Cause: the seed hands `supabase_auth_admin` an **explicit** grant, and the fix
only revokes from PUBLIC, `anon` and `authenticated`. Its EXECUTE was therefore
never at risk in that scenario. Step 5 was reading the fixture, not the fix — the
[[fixture-planted-control-never-tests-the-producer]] class.

**Fix: step 8, where the re-grant is the only thing holding login up.** It
re-seeds `supabase_auth_admin` reaching the hooks via **PUBLIC alone**, asserting
first that no direct grant remains so the scenario cannot silently degrade back
into the old one. There `REVOKE ALL … FROM PUBLIC` strips the auth service too,
and only the re-grant puts it back.

Not contrived: production renders `prune_integration_history` as
`{postgres=X/postgres,=X/postgres}` — PUBLIC is its only non-owner path — so a
hook in that shape is a live arrangement.

**The re-grant was always correct.** What was missing was any control proving it.
